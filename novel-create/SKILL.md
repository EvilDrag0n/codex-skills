# 长篇小说创作与续写

从一个念头做到能连载的长篇。先把主题、故事世界、人物和大纲落成文件，再按章写正文，往后每次续写都从文件恢复进度。成稿按活人感标准写。读者应当觉得人物在办自己的事，没有人站在旁边替作者念设定。

本 Skill 自带小说部分的活人感规则，整理自 human-writing 1.2.0 和十四份网文技巧文档，不装 human-writing 也能独立使用。

## 先判断这次做哪一段

| 用户要什么 | 先读 | 产出文件 |
|---|---|---|
| 主题、题材、立意、卖点、书名、简介 | `references/theme.md` | `设定/主题与卖点.md`、`项目说明.md` |
| 世界观、背景、力量体系、地图、金手指 | `references/world.md` | `设定/故事世界.md` |
| 人物设定、人物小传、配角与反派 | `references/characters.md` | `设定/人物设定.md` |
| 总纲、主线支线、分卷纲、章纲、伏笔、结局 | `references/outline.md` | `大纲/全书总纲.md`、`大纲/第N卷章纲.md` |
| 写一章正文，包括新书的第一章 | `references/living-prose.md`、`references/drafting.md`，写完读 `references/records.md` | `正文/第N卷/第NNN章 标题.md`、`创作记录/` |
| 续写、接着写、写下一章 | `references/continuation.md`，再读上一行的三份 | 正文、`创作记录/` |
| 初稿写完以后 | `references/revision.md` | 改定的正文 |

用户只要其中一段，就只读那一段的参考。`references/revision.md` 留到初稿写完再读，动笔前读它会让第一稿变成对着清单填空。

同一条规则在几份文件里都提到时，句子和写法以 `living-prose.md` 为准，一章怎么搭以 `drafting.md` 为准，记录的格式和同步以 `records.md` 为准。别处提到只是提醒。

## 开一本新书的路线

用户说开新书、从头写，按下面九步走。每一步的产出都落成文件。

1. 主题。读 `theme.md`，写 `设定/主题与卖点.md`。同时建 `项目说明.md`，填题材、读者、篇幅、章均字数、用户定下的和暂定的。以后每新增或改动一份文件，回来更新它的现行文件表。
2. 核心人物。读 `characters.md`，先写主角、第一配角、感情线上的人、最终对手四张卡。
3. 故事世界初设。读 `world.md`，定风格、时间地点、两三家势力、主角往上走的阶梯。
4. 全书总纲。读 `outline.md`，写主线、分卷表和每一卷的分卷纲。
5. 人物补全。顺着总纲补其余主要人物的简卡和关系表。
6. 章纲。只细化眼前要写的这一卷，写进 `大纲/第N卷章纲.md`。后面的卷只在总纲里留分卷纲。
7. 故事世界终设。顺着章纲把用得上的设定补细，用不上的不补。
8. 第一章。读 `living-prose.md` 和 `drafting.md`，写完读 `revision.md` 改一遍，跑检查脚本。
9. 落盘以后读 `records.md`，建四份进度记录和文风卡。

这个顺序有三条理由。立意管着下游，主角的气质和立意决定了世界的风格和力量的上限。人物先于情节，四个核心人物想通了，冲突会自己长出来。世界先粗后细，改世界比改主线便宜，所以先定大样，章纲出来再补用得上的细处。

## 项目目录

沿用用户已有的目录、文件名和格式。项目里已经有同用途的文件就在原处维护，不另建一套。从零开始时用下面的结构，模板在 `assets/templates/`，复制过去再填。模板里用不上的栏目删掉，不为了填满格子硬造内容。

```text
<书名>/
├── 项目说明.md              题材、读者、篇幅、章均字数、现行文件表
├── 设定/
│   ├── 主题与卖点.md
│   ├── 故事世界.md
│   └── 人物设定.md
├── 大纲/
│   ├── 全书总纲.md          主线、分卷表、各卷分卷纲、伏笔表
│   └── 第N卷章纲.md          只给眼前要写的卷建
├── 正文/
│   └── 第N卷/第NNN章 标题.md
├── 草稿/                    试写和候选片段，不算正式进度
└── 创作记录/
    ├── 文风卡.md            不随章节同步
    ├── 主要角色记录.md       进度记录
    └── 第N卷/
        ├── 已发生总结.md     进度记录
        ├── 紧接章节计划.md   进度记录
        └── 未发生待办.md     进度记录
```

四份进度记录每写完一章同步一次。文风卡只在文风或称谓有变化时更新。这套记录和 novel-continuity 用的是同一套字段，两个 Skill 可以接着维护同一个项目。

章节文件第一行是 `# 第001章 标题`，后面只有正文。一章里换场，用单独一行的 `***`。

环境不能写文件时，把同样结构的内容直接放在回复里，并提醒用户自己保存，下次续写要贴回来。

## 开工前

1. 项目已经存在时，先跑 `python scripts/novel_status.py <小说根目录>`（系统只有 `python3` 就用 `python3`）。它会列出现有资料、最新章节、章纲细化到哪一章、各份记录同步到哪一章，以及建议先读哪些文件。没有 Python 就手动按 `references/continuation.md` 的顺序读。
2. 分清哪些是用户定下的，哪些可以创造。用户写明的设定、人物、结局和禁区是硬约束。其余在授权范围内直接创造，写进文件时标上“暂定”。
3. 只在答案会改变整本书方向时提问，一次问完，最多三个。通常是题材与读者、篇幅与平台、明确不要的内容。用户说直接写、别问，就自己定，交付时把暂定项列出来。

### 缺上游资料时

用户只要下游的一段，上游却没有，比如没定主题就要大纲。这时用几句话补出最小的上游，至少包括一句话故事、主角想要什么、世界是什么风格，写进对应文件并标暂定，然后继续做用户要的那一段。不停下来把上游完整做一遍，也不假装上游已经存在。

已经在连载的书缺少会决定走向的资料，只问那个关键缺口。

### 题材不同，填的东西不同

力量阶梯、等级地图和金手指是给升级流准备的。都市、悬疑、言情、职场、历史这类写实题材按 `world.md` 的“不同题材填哪些”取舍。悬疑、推理和有大反转的书，在总纲里加一张真相与线索表。

### 现实部分的核准

故事依赖真实的历史、城市、职业、法律、医学或技术时，会改变情节的部分要查。查不了，或者用户不让花这个工夫，就照常识写，在 `项目说明.md` 的暂定项里列出没核准的条目，交付时说一声。没查的不写成查过的。

## 每一段做到什么程度算完

| 段 | 完成的样子 |
|---|---|
| 主题 | 一句话故事能让陌生人追问然后呢。主题是一个两难的问题。写得出读者持续得到什么、多久兑现一次 |
| 故事世界 | 每条设定都说得出它改变谁的行动。主角往上走的阶梯每一档有质的差别。每个活动范围有进来时的处境和离开的理由 |
| 人物 | 主要人物各有想要的、怕的、会为之撒谎的、总犯的同一个错。任意两个人的台词互换会露馅 |
| 大纲 | 主线能按卷讲出目标、阻力、高潮和代价。每个伏笔有埋设处和回收处。章纲每章写得出章末状态 |
| 正文 | 每场戏改变了一点东西。八项硬禁令清零。四份进度记录同步到这一章 |

## 写正文的硬规矩

这几条在每一章都成立，细节在参考文件里。

- 动笔前读上一章全文和 `紧接章节计划.md`。摘要不能代替上一章的原文，语气、未完的动作和情绪余波只在原文里。
- 一章只写章纲里属于这一章的事。长篇最常见的失手是一章写掉三章的纲，过程被压成概述，人物没来得及做选择。宁可这一章停得早。
- 已发生的事以正文为准，大纲和设定只管未来。不能把卷末的境界、未来的死亡和结局的关系写成人物现在的状态。
- 人物只知道他在故事里已经知道的事。作者掌握的秘密不自动属于角色。
- 设定等人物碰到再讲。第一章不交代世界，不排人名。
- 篇幅不够时加事，不加词。
- 正式章节落盘以后，在同一轮里同步四份进度记录。试写、候选片段和风格示范存到 `草稿/`，不推进连载进度。

章均字数以 `项目说明.md` 为准，用户没指定时按三千字左右写。

### 硬禁令和检查脚本

`living-prose.md` 列了八项成稿硬禁令，八项都要清零。

初稿改完以后跑 `python scripts/check_chapter.py <章节文件> --target <章均字数>`。脚本能自动判定的是其中五类，破折号、提示性冒号、叙述里的翻案句、硬停词、模型路标，报在“需要修改”里，必须清零。另外三项，三项以上的排比、给抽象名词配具体动词的抒情、章末升华，脚本只能提醒，认不全，要在改稿时自己查。“需要人工判断”的项逐条看过，人物真会这么说、这场戏确实需要就保留。

脚本只认形状。它全绿只说明没有踩禁令，这一章有没有人，要靠 `revision.md` 的七遍和最后的冷读。冷读答出来的毛病当场改掉。

## 多条规则同时出现时

1. 用户这一次明确说的话，包括文体、尺度、人称和要不要某种套路。
2. 已经写出来的正文和用户确认过的设定。
3. 现行总纲和章纲。
4. 本 Skill 的参考文件。
5. 检查脚本的提醒。

类型惯例可以盖过默认写法。系统流的面板、书信、告示这类文内文本按它本来的格式写，放进引用块（行首加 `> `）或【】里，脚本不检查这些位置的冒号。人物对白按人物说话，对白里出现的口头语不算叙述者的毛病。

发现正文和大纲有重要冲突时，记进 `未发生待办.md` 并告诉用户，不悄悄改掉已经写成的事实，也不擅自改核心结局。

## 交付

正文文件里只放小说。提纲、检查过程和修改说明不进正文。

用户只要作品就只交作品。需要汇报时写清三件事，这次完成了什么、文件在哪里、哪些是暂定或待用户定的。记录没同步完就照实说落后在哪一章，下次先补齐再续写。

不照搬现成作品的人物名、设定名和情节。同类作品只借骨架，换掉的那一块要是自己的。
